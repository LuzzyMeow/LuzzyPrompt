# 维护时机：什么时候触发索引更新

**先记住一条**：索引**不是实时维护的**。官方明确说它不是监视器、不是守护进程、
也不是第二套维护流程。README 里「自动发现代码变化」指的是**调用维护时算出漂移**——
检测是**拉取式**，必须有人调一次。

## 时机表

| 时机 | 动作 | 依据 |
|---|---|---|
| **接手项目 / 新会话开始** | 读**一次**完整认知 | 新会话通常加载一次完整认知，建立与当前仓库、索引版本、服务身份匹配的系统认知 |
| **任务进行中** | **不重载** | 只要模型还能可靠使用这份认知，就不必在每个任务或工具调用前机械重复加载 |
| **代码与测试稳定后（收尾）** | 调**一次**维护，解决待修项，用校验与指南收敛回 `aligned` | 先完成最近的稳定工作单元，跑常规的格式化、lint 与测试，**然后**维护 |
| **上下文压缩后** | **强制完整重载** + 一次完整确认 | 便宜检查点不可替代；见 `cognition-lifecycle.md` |
| **语义阈值到达** | 建议性的重载信号 | 默认 **30** 条不同语义路径变化；可配置 |
| **大阶段边界** | 可选声明阶段切换 | **不用于**完成一个函数、跑一次测试、完成一个小清单项 |

## 为什么维护只能放在收尾

**仓库不干净时会被顶回。** 存在语义漂移时，系统建议的状态是
「完成当前工作单元后再维护」——中途触发拿不到有效结果。

正确顺序：

1. 完成最近的**稳定**工作单元
2. 跑**常规的格式化、lint 与测试**
3. **然后**调一次维护
4. 解决待修项，用校验与指南**证明回到 aligned**

**不要**在每个需求末尾手动加「维护索引」——项目规则与维护流程会在受管对象变化后引导完成。
采用自动模式时，只在需要真实人工批准、必须执行外部操作、无法证明恢复、
安全检查失败、或发现第三方并发冲突时才打断用户。

## 阈值配置

团队策略住在 `.aoci/config.json`，但**用命令行改，不要手改文件**：

```bash
aoci --repo . config get cognition_refresh_threshold
aoci --repo . config set cognition_refresh_threshold 50
```

默认 30，接受 1–100000。老仓库没有这个字段时用默认值；**非法值会停止配置加载，
不会变成零阈值**。这是团队策略，本地配置**不能**覆盖。

**计数口径**：真实的语义过期、可处理的缺失、待策展的**不同路径数**。
同一个文件反复改只算一次。以下**不计入**：仅格式变化、仅换行符变化、策展排除、
技术性跳过、Git 忽略、AOCI 运行时文件、基线恢复、范围外对象。孤儿的治理单独处理。

## 维护状态的含义

| 状态 | 含义 |
|---|---|
| 不需要刷新 | 建议复用当前认知；显式请求完整认知仍然可用 |
| **等到稳定再刷新** | 先完成最近的稳定工作单元再维护 |
| **需要刷新** | 走既有维护与对齐门禁 |
| **对齐后可就绪** | 治理已就绪，完成对齐证明后可做可靠的显式认知请求 |

**刷新状态不改变显式交付模式**：普通请求仍然请求完整范围，即使状态是「不需要刷新」
或已有匹配回执。只有显式要求便宜检查点时才返回紧凑结果。

## 写失败与恢复

正式写入前整批被拒 → 索引**保持不变**。
正式写入开始后中断 → 系统保留不可变意图、写入证据与恢复状态，
按可证明的后像继续，或按精确前像回滚；遇到第三方字节冲突**失败关闭**，
不会用「继续写完」覆盖外部修改。

**终态**只有三种：`applied`、`repair_required`、`stopped`。

- `stopped` **不是成功**，也**不一定**代表没有写入——必须看失败步骤、正式写入证据
  与指南给出的恢复动作
- `repair_required` 是**有界的自动修复**（只修失败的候选，不产生正式写入）
- 无法证明的恢复状态、第三方正式字节、持续并发冲突 → **硬阻塞**，交用户

## 长任务连续性

用户问进度、问设计、问架构、问时间、报错误，都属**非控制消息**：
简洁回答、保留当前计划与运行身份、**继续既有的下一步**——**用户不需要说「继续」**。
只有明确停止、暂停、取消、回滚、改范围，或禁止提交推送，才改变任务。

## 一句话总结

**读在开头，写在收尾。**
